# IR: 异步任务调度与回滚/备份隔离 [TASK-8]

## 阶段1：DeployEngine 重构与事务隔离机制
**目标**：实现部署生命周期中“先测试再上线”的事务隔离与旧版本自动 GC。
1. **[MODIFY] `internal/application/pipeline_runner.go`**:
   - 移除 `handleSyncTask` 中的 Symlink（软链接切换）逻辑。Sync 阶段只负责传文件。
2. **[MODIFY] `internal/application/deploy_engine.go`**:
   - 在 `runDeploySteps` 方法中：
     - 若 `e.runner.Run(...)` 执行失败，直接放弃 Symlink 切换，部署任务结束为 `failed`（此时生产环境仍然保持在上一个稳定版本的软连接）。
     - 若成功，再遍历 `env.ServerIDs` 并执行 `sshClient.RunCommand(srv, symlink_cmd...)`，进行真正的原子化切换。
     - **执行自动 GC**：若 `project.KeepReleases > 0`，计算并在目标机器执行清理命令：
       `cd env.DeployPath/releases && ls -1t | tail -n +X | xargs -r rm -rf` (X = KeepReleases + 1)。

## 阶段2：持久化调度与崩溃恢复 (Crash Recovery)
**目标**：消除不可追踪的内存并发，改为由数据库作为事实来源的调度队列。
1. **[NEW] `internal/application/deploy_scheduler.go`**:
   - 引入 `DeployScheduler` 结构体，持有 `DeployService` 和 `DeployEngine` 的引用。
   - `Recover()`: 查库，将所有 `status = 'running'` 的任务更新为 `failed`。
   - `Notify(deployID uint)`: 写入本地带缓冲的 Channel。
   - `Start(ctx)`: 启动**单例 Worker**（消除并发）。从 Channel 取出 ID，验证状态，然后**同步调用** `deployEngine.RunDeployBlocking()`（原本的 `StartDeploy` 取消异步包装）。
2. **[NEW] `internal/application/deploy_scheduler_test.go`**:
   - 使用 MockService 测试其恢复逻辑与单例执行逻辑。
3. **[MODIFY] `internal/application/deploy_service.go`**:
   - 在 `TriggerDeploy` 中，不再直接调用引擎，而是在数据库创建状态为 `pending` 的记录后，调用 `scheduler.Notify(deployment.ID)`。
4. **[MODIFY] `cmd/pdeploy/main.go`**:
   - 实例化 `DeployScheduler`，调用 `Recover()` 并在后台启动 `Start(ctx)`。
