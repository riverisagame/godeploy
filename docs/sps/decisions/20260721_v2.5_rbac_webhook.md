# 架构决策与需求对齐 (v2.5: RBAC & Webhooks)

## 1. 现状分析
在之前的简化中（2026-07-19），系统移除了复杂的权限系统和 webhook 自动触发，转为单机单用户模式。但由于 `[TASK-3]` 要求重新实现「RBAC 权限与 Webhook、通知」，我们需要明确以下需求范围：

### 1.1 RBAC 权限系统
目前系统中 `main.go` 启动时默认创建了一个 admin 账号。路由中间件已经区分了 `RequireAdmin` 和普通的 `protect`。
**缺陷**：缺少用户管理 API。
**对冲与攻击**：如果只保留一个 admin，那就没有 RBAC 的意义。所以必须增加一个 `/api/users` 接口供 admin 创建 `developer`（操作员）账号。操作员只能执行部署和查看日志，不能修改项目和服务器配置。

### 1.2 Webhook 自动部署
**现状**：`WebhookHandler.HandleGitHubPush` 目前是一个空桩。`Project` 模型中有 `WebhookSecret` 字段。
**对冲与攻击**：为了防范重放攻击和恶意请求，必须严格校验 GitHub 传来的 `X-Hub-Signature-256`。只有签名合法，并且匹配对应的分支，才能触发对应的 `Environment` 部署。必须考虑防抖（Debounce）或者避免并发拉取引起的锁竞争。但在目前的 `DeployEngine` 中，已经有了 `runningDeploys` 防并发控制。

### 1.3 部署通知
**现状**：`Environment` 中存在 `NotifyWebhook` 字段，但在 `DeployEngine` 中没有任何调用。
**对冲与攻击**：网络请求不能阻塞主部署流程，所以通知必须在单独的 goroutine 中执行，带有超时机制（比如 5 秒），且不能因为通知失败而将部署标记为失败。

## 2. 计划与影响面评估
1. **用户管理**：增加 `/api/users` CRUD 接口（仅 Admin）。影响面：新增 `user_handler.go`，并在 `router.go` 中注册。
2. **Webhook**：补全 `webhook_handler.go` 逻辑，解析 Push Event，触发部署。影响面：修改 `WebhookHandler`，仅依赖现有 `StartDeploy` 逻辑。
3. **通知发送**：在 `deploy_engine.go` 的 `runDeploySteps` 最后增加 HTTP POST 请求。影响面：`deploy_engine.go` 会发起外部网络请求。

## 3. 性能与安全性考量
- **性能对冲**：通知必须异步且设定短超时（Timeout=5s）。
- **安全攻击**：Webhook 必须使用 `crypto/hmac` 做 `sha256` 常数时间比对（`subtle.ConstantTimeCompare`），防止时序攻击。密码存储必须继续使用 bcrypt（当前已具备）。
