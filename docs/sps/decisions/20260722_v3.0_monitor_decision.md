# ADR: TASK-6 监控指标与增强型 Webhook 架构决策

## 1. 监控指标选型
- **否决方案**: 手写数据库表用于统计，并在前端提供 Dashboard 图表渲染。这种做法引入了复杂的聚合查询、存储压力以及前端图表依赖（例如 ECharts），对于一个轻量级部署引擎属于过度工程 (Over-engineering)。
- **决策方案**: 集成官方 `prometheus/client_golang`。
  - 直接在内存中统计（通过原子操作保证并发安全，延迟 < 1ms）。
  - 提供无鉴权的 `/metrics` 标准接口，交由专业的监控系统（Prometheus + Grafana）去抓取和展示。
  - 核心指标包括：HTTP 响应时长/状态分布、发布总次数（成功/失败区分）、发布耗时分布、当前正在运行的并发发布任务数。

## 2. 增强型 Webhook 推送
- **痛点**: 原逻辑在 DeployEngine 中生硬地起了一个 Goroutine 执行 http.Post，导致发布通知可能因为临时网络抖动而静默丢失，且无从得知状态；只支持发布成功这一种事件。
- **否决方案**: 引入 Redis/RabbitMQ 或基于 SQLite 建表进行离线定时重试。单体系统没必要引入外部组件或过度复杂的扫表轮询。
- **决策方案**: `WebhookDispatcher` (异步内存队列)。
  - 在应用层启动一个专职的单例/或随服务生命周期的 Dispatcher。
  - 使用带有 Buffer 的 Channel 接收发布事件（DeployStart, DeploySuccess, DeployFailed）。
  - 每个事件在一个限流的 Goroutine Worker 中消费，遇到非 `2xx` 返回或超时时在内存中重试（上限 3 次，指数退避），确保最高限度的弱一致性，同时与部署主流程物理隔离。

## 3. 增强型 Webhook 接收
- **现状**: 只支持 GitHub 的 `X-Hub-Signature-256`。
- **决策**: 扩展兼容 GitLab (`X-Gitlab-Token`) 及 Gitee (`X-Gitee-Token`)。直接对现有代码做向下兼容扩展，提取公共的验证/分发接口。
