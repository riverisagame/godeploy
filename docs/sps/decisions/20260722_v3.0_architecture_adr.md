# Architecture Decision Record: v3.0 (CI/CD Pipeline, Audit, Monitor, Backup)

## 1. 背景与目标
在顺利完成 v2.5 的核心重构及 RBAC/Webhook 后，系统面临向企业级 CI/CD 与高可用管理平台的演进。
目标为四大模块：流水线编排、审计日志、监控报警、回滚与冷备。

## 2. 决策与选型

### 2.1 流水线编排 (DAG: Build -> Test -> Deploy)
*   **选型**: 遵循 GitOps 原则，弃用繁杂的 UI 表单，采用在目标代码仓库根目录读取 `.pdeploy.yml` 的方式解析 DAG。
*   **执行隔离**: 引擎宿主机将支持通过基于 Docker 的 Worker 或在宿主机的隔离目录执行 Build/Test。为防止接口超时，所有流水线任务强制进入异步 Worker Pool。

### 2.2 审计日志 (Audit Log)
*   **选型**: 新增 `audit_logs` 表，记录核心维度的操作：`user_id, action, target_type, target_id, details, created_at`。
*   **性能考量**: 不做重量级的行级别 Diff 存储以避免体积膨胀。引入定时/异步清理机制（如保留近 90 天数据）。

### 2.3 监控与报警 (Prometheus & 丰富的 Webhook)
*   **选型**:
    *   引入 `prometheus/client_golang` 暴露 `/metrics` 供内部抓取（包含并发数、部署耗时、成功率等）。
    *   Webhook 扩展模型：在原有的基础上增加 `webhook_type` 字段（Generic, DingTalk, Feishu, WeCom），在后端的 payload 组装层根据类型执行策略模式。

### 2.4 回滚演练与数据冷备
*   **选型**:
    *   冷备解耦：不再强行耦合进同步发布主流程。作为 DAG 中的一个独立异步节点（如 `pre-deploy` 或单独的 `backup` 任务）执行。
    *   演练定义：回滚演练定义为健康检查和脚本干跑（Dry Run），不实际切换线上流量（不修改 active symlink）。

## 3. 风险抵御与对冲
*   **负载爆炸风险**: 引入 DAG 和编译将消耗大量 CPU。**对冲方案**: 必须通过 goroutine pool 严格限制同时执行的 Pipeline 数量。
*   **接口超时风险**: 长耗时任务不可阻塞 HTTP 请求。**对冲方案**: 采用异步排队机制，前端引入轮询 (Polling) 或 WebSocket 接收进度更新。
