# ADR: Pipeline 与 DAG 架构决策

## 状态
- 提出日期：2026-07-22
- 状态：已接受 (用户批准)
- 关联任务：[TASK-7]

## 背景
用户要求实现类似 GitOps 的声明式 `.pdeploy.yml` 并且可能采用 DAG (有向无环图) 来进行依赖执行。
但是在本项目的单机轻量级 Go 架构和 SSH 分发场景下，真正的 DAG (带并发、任务状态依赖图、事务回滚等) 极易引发高技术债：
1. Goroutine Leak。
2. 并发导致的 SSH 连接风暴或死锁。
3. OOM 和单机内存状态过载。

## 决策
我们决定**拒绝 DAG 并发引擎**，转而采用**线性 Stages 模型**（类似 GitLab CI 的架构）：
- `Stage` 为严格串行执行阶段 (例如 pre_build -> build -> deploy -> post_deploy)。
- 同一个 `Stage` 内的 `Tasks` 按照定义顺序线性执行，不支持并发。
- 支持 `local` (控制机) 与 `remote` (目标机) 两种执行环境。
- `sync` 将作为内置的特殊保留 `type` 来替换手动脚本传输。

**如何做到向下兼容且优雅重构？**
- 引入统一的 `PipelineRunner` 组件。
- 当项目中不存在 `.pdeploy.yml` 时，`DeployEngine` 不会再使用硬编码的分支逻辑，而是自动构建一个包含 `[deploy, post_deploy]` stage 的**默认 Pipeline 内存对象**，然后丢给 `PipelineRunner`。这能实现 100% 的抽象统一，杜绝新老逻辑并存的屎山代码。

## 影响
- 需要引入 `gopkg.in/yaml.v3` 进行解析。
- `deploy_engine.go` 将变得更轻量，原本庞大的同步和执行逻辑将剥离至 `PipelineRunner`。
