# ADR: 异步任务调度与回滚/备份隔离决策

## 状态
- 提出日期：2026-07-22
- 状态：已接受 (用户批准：大厂方案+极致简洁)
- 关联任务：[TASK-7]

## 背景
大厂在部署系统时，必须保证两条铁律：
1. **任务防丢与防冲突**：部署中途进程挂掉不能导致状态黑洞，同时不能两人并发部署同一个项目。
2. **磁盘防爆与容错隔离**：服务器磁盘不能被无限的旧版本挤爆，且部署失败必须能干净地回退。

为了在单机架构下满足上述大厂标准，同时保持不引入 Redis/MQ 等外部依赖的极致简洁，我们做出以下决策。

## 决策

### 1. 复用 `Deployment` 作为持久化队列 (Async Scheduling)
- **取消直接的内存并发**：`DeployService` 收到部署请求后，仅负责创建一条状态为 `pending` 的 `Deployment` 数据库记录，不再拉起 goroutine。
- **单例轮询 Worker**：在后台启动一个简单的 Worker，轮询/接收 `pending` 状态的任务进行派发执行。
- **崩溃恢复 (Crash Recovery)**：每次应用启动时，扫描数据库将所有处于 `running` 的异常任务置为 `failed`，并记录崩溃原因，彻底解决状态僵死。

### 2. Immutable Releases 与自动垃圾回收 (GC & Rollback)
- **利用已有字段 `KeepReleases`**：在项目配置中早已预留了该字段。部署成功后，`DeployEngine` 通过 SSH 执行命令列出远端 `releases/` 下的文件，保留最新的 N 个，并强制 `rm -rf` 清理老旧版本。
- **事务性隔离保护**：如果发布脚本执行中途报错，除了标记任务失败外，不会修改原有的 `current` 软链接（新版本目录就当成废弃资产交由下一次的 GC 清理），确保业务 **0 宕机**。
